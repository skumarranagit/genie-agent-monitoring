The problem

Genie already logs a lot — but it's spread across four places

Answering "who asked what, what did Genie run, on which data, and was the answer any good?" today means stitching together sources that each hold one piece of the story.

Audit log

Who did what, when, from where — but IDs only; no prompt or answer text.

Query history

The SQL Genie executed, who ran it, duration, rows — but not the question that produced it.

Lineage

Which tables and metric views were read — keyed by statement, not by conversation.

Conversation API

The prompt, answer, reasoning and feedback notes — but lives in the agent, not in a governed table.

Compliance & audit

Retain the full question/answer record in your own table, independent of conversation deletion.

Answer quality

Find thumbs-down answers, read the reviewer's note, and see the exact SQL and tables behind them.

Adoption & cost

Questions per agent, users, SQL latency and rows scanned — one place, filterable.

-- thumbs-down answers this week, with the reviewer note and the tables Genie used
SELECT created_ts, user_email, prompt_text,
       filter(feedback_notes, n -> n.content IS NOT NULL)[0].content AS note,
       transform(lineage_sources, l -> l.name)                          AS tables_used
FROM   <catalog>.genie_monitoring.message_trace
WHERE  feedback_rating = 'NEGATIVE' AND created_ts >= current_date() - INTERVAL 7 DAYS
ORDER  BY created_ts DESC;

PROFILE=<cli-profile> SPACE_ID=<genie-space-id> WAREHOUSE_ID=<sql-warehouse-id> \
  ./scripts/deploy_all.sh                              # notebook → job → app → grants
databricks jobs run-now <job_id> \
  --json '{"job_parameters":{"lookback_days":"0"}}'   # one-time backfill of history

Prerequisites

  • Unity Catalog workspace with system tables enabled (access and query schemas).
  • Job run-as identity with CAN MANAGE on each Genie Agent (required to list every user's conversations) and SELECT on the three system tables.
  • A SQL warehouse for the app; serverless compute for the job.
Limits & FAQ

Known behaviour and design choices

Is it real-time?

Near-real-time. Text and feedback arrive on the next run (≤30 min); execution, lineage and audit follow system-table latency (typically 10–60 min). The 2-day lookback fills them in automatically.

Who can see the prompts?

The table contains every user's questions and copies of query results. The reference app reads as its service principal, so gate it with app permissions — and apply the grants, governed tags and ABAC policies in Security & access control.

Questions routed from Genie One

When Genie One routes a question into a Genie Agent, the agent-side message is captured, but the audit log has no Genie Agent "create" event; user identity is resolved from the user ID instead.

What if a user deletes a conversation?

Deletion in Genie removes it for everyone; the bronze table keeps the raw payload already ingested, so the record is retained under your policy.

Scale

API calls scale with conversations in the lookback window; each agent supports up to 200,000 conversations. For many agents, run one task per agent or loop over agents in the notebook.

What about bias and answer quality?

The trace makes interpretation issues visible (e.g. ambiguous "top" or "Medicare" mappings). Pair with Genie benchmarks and clarification rules to measure and improve over time.

Security & access control

Recommended: treat the trace tables as sensitive by default

The trace tables hold users' prompts, answers, identities and copies of query results — and those copies do not inherit the source tables' row filters or column masks. Do not open them for general-purpose access. These are recommendations; the blueprint ships with plain grants only.

1

Lock down with grants

Dedicated restricted schema. Access only for a reviewers group, the ingest job service principal and the app service principal — no broad groups. Owner = group or service principal.

2

Tag sensitive columns

Governed tags: prompt (prompt, feedback), model_output (answer, reasoning, agent steps with result rows), identity (email, IP, user agent), raw (raw payloads).

3

Two ABAC policies

Column mask: redact tagged columns except for reviewers and the ingest job. Row filter: agent owners see only their own agents; everyone sees their own questions.

4

Split the data model

message_metrics (IDs, ratings, SQL stats, lineage — shareable) and message_content (prompts, answers, steps, notes — reviewers only). Keeps masking simple.

5

App respects ABAC

Switch the app to on-behalf-of-user so each viewer sees only what policies allow — or at minimum restrict who can open the app.

6

Test before production

Query as a non-exempt user; confirm masks and filters apply and that the ingest job and app still work.

Watch-outs (per Databricks ABAC docs): put the ingest job in every policy's EXCEPT; only one row filter per table and one mask per column can apply to a user — overlaps (or manual filters/masks on the same table) block access; readers need serverless or DBR 16.4+; clones and Delta Sharing fail for non-exempt principals; add retention and a purge process. Verify in your workspace: SQL warehouse support, whether owners/admins bypass policies, and mask behaviour on writes and time travel. Full guidance: SECURITY.md.
